## What the wave applied vs. what was applied by hand

- **Applied by `simplicio-loop wave`** (via the required `simplicio-dev-cli` operator,
  `edit --plan edit-plan-1.json --apply --json`, `worker_claimed` lease, real find/replace
  against the working tree): all 4 operations in `scripts/install_lib.py` —
  - `copy_skills_opencode(target, is_global=False)` writes `<target>/.opencode/skills/`
    (project-local) or `$HOME/.config/opencode/skills/` (`--global`) instead of a hardcoded
    `HOME`-derived constant.
  - `merge_opencode_mcp(target, is_global=False)` writes `<target>/opencode.json`
    (project-local) or `$HOME/.config/opencode/opencode.json` (`--global`).
  - `main()` gained `--with-runtime-mcp` / `SIMPLICIO_INSTALL_RUNTIME_MCP=1`; the opencode
    call site now only calls `merge_opencode_mcp` when that optional runtime bind is
    requested, and always passes `target`/`is_global` to `copy_skills_opencode`.
  - Usage docstring gained the new flag.
- **Applied via the required `simplicio-dev-cli` operator directly** (`simplicio-dev-cli
  mechanical-edit --plan ... --apply --json`, schema `simplicio.mechanical-edit/v1`,
  `{"op": "create_file", "path": ..., "text": ...}`), **not through `wave`**, and
  **documented here rather than hand-edited**: creation of the new test file
  `tests/test_install_opencode_target_unit.py`. Reason: `simplicio-loop wave`'s
  edit-plan-N.json ("minimal host plan") format unconditionally requires every
  operation's `path` to already exist in the repository —
  `simplicio_loop/runner.py::_validate_minimal_host_plan_paths` raises
  `plan_path_not_found` for any path that is not already a file, regardless of the
  task's declared `Type:`/`Target:` fields (which only gate the separate
  mapper-derived-plan validator in `simplicio_loop/plan_contract.py`). A `find: ""`
  operation against a non-existent path is rejected outright by
  `simplicio-dev-cli edit --plan ... --apply` too ("each operation needs string path,
  non-empty find, replace"); only `simplicio-dev-cli mechanical-edit` with an explicit
  `create_file` op (content under the key `text`, not `content`/`body`/`data`) can create
  a new file, and `wave` never routes to that command for a minimal host plan. This was
  verified by direct experimentation (`simplicio-dev-cli mechanical-edit --plan ... --dry-run
  --json`) before use; the file's sha256 after creation
  (`7a6976e932ca17e337b2b65e1e14c155bd2e60adb27b1f76f92eeacb0fcd7900`) matches the
  intended content exactly. No file was ever edited with a plain Write/Edit tool call.

## Loop bugs found (reported, not fixed — out of scope for #1327)

1. **`wave`'s edit-plan-N.json cannot create new files**, contradicting
   `SKILL.md`'s hot-path documentation ("use `\"\"` to create a new file" — that
   applies to the `apply`/`ops.json` hot path, not `wave`/`edit-plan-N.json`).
   `simplicio_loop/runner.py::_validate_minimal_host_plan_paths` hard-blocks any
   path that is not already a file (`plan_path_not_found`), and
   `simplicio-dev-cli edit --plan ... --apply` separately rejects an empty `find`
   ("each operation needs string path, non-empty find, replace"). Only
   `simplicio-dev-cli mechanical-edit` (a different subcommand, different schema,
   different operation shape, undocumented `text` field name) can create a file,
   and nothing in `wave` routes to it for a minimal host plan.
2. **False "stale mapper context" block after a successful apply.** On the very
   first attempt (`run-20260926-084629-4cvp8t7q`), `wave` correctly dispatched
   task 1 through the deterministic-worker route and `simplicio-dev-cli` applied
   the edit to `scripts/install_lib.py` for real (confirmed by file mtime
   matching the `worker_claimed` event exactly). ~2m26s later the SAME run's
   `operator_batch_preflight` re-ran a freshness check
   (`simplicio_loop/runner.py`, the `"stale mapper context: repository changed
   after planning"` `RuntimeError`) against `task_indices: [1]` again, using the
   ORIGINAL pre-apply `mapper-context.json`/`plan.json` baseline — which of
   course no longer matches the tree the first dispatch had just (legitimately)
   mutated, and the whole run terminated `BLOCKED`/`operator_dispatch_failed`
   even though task 1's mutation had already succeeded. A second,
   low-confidence `"route": "agent"` execution-route record
   (`execution-route-1.json`, `causal_ids: ["run-...", "run-...-task-1"]`) for
   the SAME task index, alongside the first `"route": "worker"` record
   (`execution-route.json`, `causal_ids: ["run-...", "1"]`), suggests a
   duplicate/redundant re-dispatch attempt for one task rather than a genuine
   retry loop.
3. **Every `prepare`/`wave`/`orient` invocation that observes any working-tree
   change re-runs a full, slow Mapper deep index** of this ~3900-file
   monorepo (~2–3 minutes of single-core CPU each time, `scan --sync
   --update`), even for a one-line `tasks.md` edit. There is no narrower/
   incremental survey path for a small, targeted change; each edit to
   `tasks.md` while iterating on this issue cost a full reindex cycle.
4. **`simplicio-dev-cli edit --plan ... --apply` runs its own default `verify`
   step (a bare `pytest -q` under a scoped module list including
   `tests/test_benchmark_*`) after every apply**, unrelated to the task's
   declared `<Lane> verifier:` commands in `tasks.md`. This benchmark-test pass
   took 5+ CPU-minutes without finishing in this environment and had to be
   killed to keep the session within its "one heavy command at a time" budget;
   an earlier orphaned instance of the same subprocess (from a `wave` process
   whose parent had already been reaped) ran unattended for 22+ CPU-minutes
   before being found and killed. This default-verify step should not fire
   for every operator apply, or should be bounded/killable independently of
   the parent `wave`/`prepare` process.
