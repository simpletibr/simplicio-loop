# Issue #1339 — wave evidence

`orient --brief` (and plain `orient`) on a large repo used to block for 4.5+
minutes and could print nothing parseable. Fixed with TDD, delivered against
THIS worktree (`/home/user/wt/i1339`, the ~3,900-file monorepo, branch
`fix-1339-orient-large`).

## Root cause

`_ensure_project_map()` (`simplicio_loop/cli_impl.py`, issue #1328/#1331) ran
a fully synchronous `simplicio-mapper index <repo> --json` on a cold repo,
with no budget wrapping the whole `orient`/`orient --brief` call. Measured
here: **5m8.742s** wall time for a genuinely cold `orient` on this monorepo
(`scratchpad/orient-cold.time`, reproduced live during this delivery) — past
any reasonable foreground budget, and past the point a caller piping the
output into `json.tool` would still be waiting with nothing on stdout.

## What changed (source, not evidence)

All in `simplicio_loop/cli_impl.py`:

1. **`_orient_budget_seconds()`** — new wall-clock budget for the whole
   `orient`/`orient --brief` call, default 120s, `SIMPLICIO_LOOP_ORIENT_BUDGET_S`.
2. **`_ensure_project_map(root, *, budget=None)`** — additive: `budget=None`
   (every pre-#1339 caller, e.g. `prepare`) keeps the original fully-blocking
   behavior byte-for-byte (`tests/test_ensure_project_map_reuse_unit.py`
   unaffected). With a budget (used only by `orient`/`orient_brief`), the cold
   index is launched **detached** — `subprocess.Popen` with
   `start_new_session=True` (its own process group), stdout/stderr to
   `.simplicio-loop/mapper-index.log` — instead of blocking; polled up to
   `budget` seconds.
   - Still running at the deadline → `MapperIndexTimedOut` (reason_code
     `mapper_index_timeout`); the process is left running in the background,
     never killed.
   - A lock file (`.simplicio-loop/mapper-index.lock`, `{pid, started_at}`)
     records the background attempt; a call while it is still alive raises
     `MapperIndexRunning` (reason_code `mapper_index_running`) instead of
     starting a second index or blocking again.
   - `_mapper_index_running_info()` lazily kills the WHOLE process group
     (`os.killpg(pid, SIGKILL)`) and drops a lock whose process has outlived
     the old hard cap (`_mapper_index_timeout_seconds()`, default 300s) —
     "kill the process group on timeout" without a separate persistent
     watchdog.
   - **`_mapper_index_reconcile_finished()`** (added during this same
     delivery, see "What TDD caught" below) — once the previously-backgrounded
     process has exited on its own, this reads its log envelope and, if it
     succeeded, reuses it (writes `mapper-index-state.json`) instead of
     starting a redundant new index. Without this, a caller polling after a
     `mapper_index_timeout` would see "process gone" and reindex from
     scratch forever, never actually reusing the background work — the exact
     reuse issue #1331 already fixed for the unbounded path.
3. **`orient()`/`_orient_impl()`** and **`orient_brief()`/`_orient_brief_impl()`**
   — both are now thin, exception-safe wrappers: any exception raised inside
   the real implementation (Fast, Mapper, `_ensure_project_map`) is caught and
   rendered as a typed BLOCKED JSON payload (`reason_code: orient_internal_error`)
   instead of leaving stdout empty. The `_ensure_project_map` call site is
   wrapped in `except (MapperIndexTimedOut, MapperIndexRunning)`, rendering
   `_mapper_index_budget_payload()` — a valid JSON envelope carrying the typed
   `reason_code` and the literal next command to run.

### What TDD caught (genuine bugs, not test-writing mistakes)

The wave's real pytest run failed **3 of 5** new tests on the first
delivery:

1. `test_ensure_project_map_bounded_raises_timed_out_then_running` — a
   **genuine reconciliation gap** in the new code: once a call raises
   `MapperIndexTimedOut` and returns, nothing keeps polling that background
   process. The NEXT call correctly saw (via `_mapper_index_running_info`)
   that the process had since exited, but had no way to tell it had
   **succeeded** — so it started a brand-new index instead of reusing the
   finished one. Fixed with `_mapper_index_reconcile_finished()` (see above).
2. `test_orient_brief_prints_valid_json_with_timeout_reason_code` /
   `test_orient_non_brief_prints_valid_json_with_timeout_reason_code` — a
   **test-design bug**: with `fast_mode="off"`, `_orient_core` falls through
   to the Mapper-`orient`-fallback subprocess *before* ever reaching
   `_ensure_project_map`; the fake mapper script only implemented `index` and
   exited 1 on `orient`, so `_orient_core` itself blocked early (with the
   pre-existing, no-`reason_code` Mapper-fallback-failure shape), and my new
   budget path was never exercised. Fixed by making the fake script answer
   any non-`index` subcommand immediately with a trivial READY envelope.

Both fixes were re-verified locally (all 5 new tests green, then the full
74-test regression set green) before being re-applied.

### How the fix increment was delivered

The corrected edit-plan was re-applied through the **required bound
operator**, `simplicio-dev-cli edit --plan ... --compile ... && edit --plan
<compiled> --apply --check '<pytest cmd>' --json` — the same mutation path
`wave` itself uses. `mutation_receipt.final_status: "applied"`,
`verification.status: "passed"`, `pytest -q tests/test_orient_mapper_index_budget_unit.py`
→ `5 passed in 4.33s`.

**This one increment did not go through `simplicio-loop tick`/`resume`/`wave`
on the SAME `run_id`**: task-index 1 was already recorded `completed` in that
run's dispatch state (dev-cli's own `execution_state: applied` is what the
wave dispatcher treats as success, even though the nested
`mutation_receipt.verification.status` had failed) — `tick`, `resume`, and a
second `wave` call on `run-20260926-162113-wpq8p4i7` all returned the exact
same stale receipt (`operator-receipt.json` unchanged mtime, `updated_at`
unchanged) without re-invoking the operator or re-running pytest, even after
`edit-plan-1.json` was overwritten with the fix. `simplicio-loop verify`
likewise still reports `coverage.scenarios.verified: 0/5` for this run_id,
since that bookkeeping is only updated by the loop's own dispatch, which this
increment bypassed. This is a genuine gap in the loop's retry path — a
task-index already marked "completed" (by `execution_state`) cannot be
re-verified in place even when its own nested verification failed and a
follow-up edit-plan fixes it — worth its own follow-up issue; it is out of
#1339's scope to fix here. The FIRST delivery (creating the test file +
writing the main implementation) genuinely went through `prepare` → `wave`
end to end, including a real (if initially failing) post-apply verification.
