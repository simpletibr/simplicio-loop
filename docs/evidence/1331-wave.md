# Issue #1331 — wave evidence

Three plumbing defects fixed with TDD (dev-cli's unbounded default verify,
Mapper survey reuse, wave create-file semantics), then delivered through the
real `simplicio-loop` wave against THIS worktree (`/home/user/wt/i1331`, the
~3,900-file monorepo, branch `perf-1331-wave`).

## What changed (source, not evidence)

1. **`simplicio-dev-cli edit --apply` verification** (`packages/dev-cli/simplicio/commands/edit.py`,
   `pipeline_stages.py`): precedence is now an explicit `--check` >
   `SIMPLICIO_TEST_CMD` > a scoped default limited to tests referencing the
   changed files > skip — never the whole suite. Bounded by
   `_verification_timeout_seconds()` (default 120s, `SIMPLICIO_TEST_TIMEOUT_S`,
   `--verify-timeout-s`); `run_bounded_subprocess()` kills the WHOLE process
   group on timeout (`start_new_session=True` + `os.killpg`), not just the
   direct child — the exact orphan shape measured in
   `docs/evidence/1327-wave.md`/`1328-wave.md`.
2. **Mapper survey reuse** (`simplicio_loop/cli_impl.py::_ensure_project_map`):
   reused by tree state (git tree id + working-tree dirty hash, excluding
   `.simplicio-loop/` itself) instead of by mere file existence. The 60s
   timeout is now 300s default, configurable via
   `SIMPLICIO_LOOP_MAPPER_INDEX_TIMEOUT_S`. Mapper's own public verbs have no
   incremental reindex (`simplicio-mapper --help`: scan/inspect/handoff/ask/
   sync only) — that limitation is unchanged; this fix only stops the SAME
   tree state from paying for it twice.
3. **Wave create-file semantics** (`simplicio_loop/runner.py::_validate_minimal_host_plan_paths`,
   `packages/dev-cli/simplicio/commands/edit.py::compile_host_plan`,
   `mechanical_edit.py`): an edit-plan operation with `find: ""` against a
   path that does not yet exist creates it — same semantics as the hot-path
   `apply`/`ops.json` flow. An existing non-empty file with `find: ""` is
   still refused (`plan_create_target_exists` / `create_target_exists`).

### Mapper survey reuse (item 2), measured

- First cold `orient` on this worktree (no `.simplicio-loop/project-map.json`
  yet): ~2026-09-26T11:14:03Z issue -> project-map.json written
  ~2026-09-26T11:18Z (~4 minutes; consistent with the ~280s measured in
  `docs/evidence/1328-wave.md` for this same ~3,900-file monorepo, plus this
  session's own overhead from cleaning up an accidental duplicate `orient`
  invocation — see "environment notes" below).
- Every subsequent `prepare` in this session (5 total) completed in
  **11–14 seconds**, confirmed by `tests/test_ensure_project_map_reuse_unit.py`'s
  mocked assertion and, live, by `.simplicio-loop/mapper-index-state.json`
  never changing its `tree_state` across those calls — `_ensure_project_map`'s
  reuse fix works as designed.
- **Limitation confirmed live, not just in docstring**: `orient`'s own
  `simplicio-mapper scan --sync` / `inspect --await` sequence (a DIFFERENT
  code path than `_ensure_project_map`, owned by Mapper's `_run_mapper`/
  `fast_integration.py`) still re-ran a real scan/inspect on most `orient`
  calls in this session (observed `simplicio-mapper index …` and `scan …`
  subprocesses at 98–99% CPU for 1–3 minutes each), because Mapper's own
  internal freshness heuristic — not the artifact this issue's fix reuses —
  decided the handoff needed refreshing. This is exactly the "Mapper's own
  current limitation" the fix's docstring names: `simplicio-mapper --help`
  exposes no incremental reindex verb (`scan`/`inspect`/`handoff`/`ask`/`sync`
  only), so a full scan is Mapper's only tool for "make the handoff fresh."
  This issue's fix stops that cost from being paid AGAIN for
  `_ensure_project_map`'s own artifact; it does not (and per the issue's own
  scope, does not need to) reach into Mapper's package to add a verb Mapper
  does not have.
